# CatAni 구현 방향성

작성일: 2026-09-08. 기존 `CatAni_Plan.md`를 검토한 후 작성한 구현 제안이다. 애드온 구현이나 샘플 리그의 실제 동작 검증은 수행하지 않았다.

## 1. 권장 방향

**개발 에이전트로 동작 생성 코드와 레시피를 제작하고, 애드온은 검증된 레시피를 로컬에서 실행한다. 자연어 입력은 선택적 로컬 LLM으로 연결한다.**

자체 구축의 중심은 대형 모션 모델의 학습이 아니라, CatAni가 소유하는 동작 라이브러리·절차적 생성 엔진·리그 어댑터다. 캐주얼한 동작은 준비 자세, 주요 포즈, 타이밍, 과장, 후속 움직임을 명시적으로 제어하는 방식부터 검증할 가치가 있다. 실제 품질은 샘플 캐릭터의 재생 결과로 판단한다.

| 접근 | 비용·운영 특성 | 판단 |
| --- | --- | --- |
| 개발 에이전트 + 절차적 모션 + 자체 포즈 | 개발 시 사용하는 에이전트 비용·한도는 별도. 애드온 생성에는 API 호출 불필요 | 핵심 구현 |
| 로컬 LLM으로 자연어를 레시피로 변환 | 모델 다운로드·메모리·추론 시간 필요 | 엔진 검증 후 선택 기능 |
| MDM·HY-Motion 로컬 추론 | GPU/메모리, 설치, 리타게팅, 이용 조건 검토 필요 | 후속 비교 실험 |
| 자체 모션 모델 학습 | 학습 데이터와 연산 자원, 품질 평가 체계 필요 | 초기 범위 제외 |

기본 모드는 오프라인으로 실행한다. 로컬 LLM까지 연결하면 제한된 동작 범위에서 자연어 생성 경험을 제공할 수 있다. 프리셋 모드만으로 범용 AI 모션 생성이라고 표현하지 않는다. 새로운 동작은 개발 에이전트와 제작자가 레시피를 추가해야 한다.

## 2. 현재 확인된 상태와 첫 결정

- 현재 작업 폴더는 Git 저장소가 아니다. `Blender/CatAni_Plan.md`와 `Blender/Player_Animation_01.blend`가 존재한다.
- 샘플의 본 계층, 기존 Action, IK/FK, Blender 버전, 장비 성능은 아직 확인하지 않았다.
- 계획상 최초 대상은 리깅된 이족 캐릭터 한 종류다. 사족 캐릭터라면 지지 다리와 보행 설계를 별도로 바꿔야 한다.
- 구현 시작 시 샘플의 복사본에서 리그를 조사하고, Blender 지원 버전 하나와 기준 리그 프로필 하나를 고정한다. 처음부터 Rigify와 Mixamo 전체를 지원하지 않는다.

## 3. 에이전트를 활용하는 구체적인 방법

개발 과정의 에이전트와 사용자가 실행하는 애드온을 분리한다.

1. **동작 설계 역할:** 요청을 시작·준비·주요 동작·정착 구간으로 나누고, 주요 포즈와 접촉 구간을 정의한다.
2. **구현 역할:** 순수 Python 동작 함수, JSON 레시피, Blender 연결 코드를 작성한다.
3. **검증 역할:** 격리 Blender에서 생성·베이크·재로드하고, 발 접촉·루프·관절 튐을 측정한다. 정면·측면 재생도 확인한다.
4. **수정 역할:** 오류 프레임과 수치를 근거로 파라미터 또는 코드를 수정한다. 제한된 횟수의 수정 뒤에도 실패하면 제작자에게 검토를 넘긴다.
5. **라이브러리 등록:** 제작자가 승인한 레시피와 기준 결과만 다음 버전에 포함한다.

기존에 사용하는 개발 에이전트는 이 반복 작업에 활용한다. CLI 실행 파일이 로컬에 있다는 이유만으로 모델 추론까지 로컬이거나 무제한 무료라고 가정하지 않는다. 계정·구독·사용량 조건과 독립적으로 애드온의 기본 생성 경로는 작동해야 한다.

런타임에는 임의 Python 코드 생성·실행을 넣지 않는다. LLM을 쓰더라도 허용된 동작과 파라미터만 반환하게 한다. 지원하지 않는 요청은 설명과 지원 동작 선택으로 돌려보낸다.

## 4. 실행 파이프라인

```text
프리셋·슬라이더 ──────────────────┐
자연어 → 선택적 로컬 LLM ────────┤
                                ↓
                       MotionSpec 검증
                                ↓
                 동작 레시피 + 스타일 파라미터
                                ↓
                  표준 포즈·접촉·루트 궤적 생성
                                ↓
                   대상 리그 변환 + 접촉 보정
                                ↓
                  별도 미리보기 Action → 베이크
```

### MotionSpec 계약

예: “오른손으로 천천히 두 번 인사해 줘”는 `wave`, `right`, 두 번 반복, 지정 길이로 변환한다. 다음 JSON은 구현 시 사용할 계약의 예시다.

```json
{
  "schema_version": 1,
  "motion": "wave",
  "duration_sec": 3.0,
  "side": "right",
  "repeat_count": 2,
  "style": "friendly",
  "intensity": 0.6,
  "loop": false,
  "root_mode": "in_place",
  "seed": 42
}
```

동작별 필수 필드·열거값·수치 범위·조합 가능 여부를 검증한다. 생성 시간과 반복 횟수로 주기를 계산하여 속도 지시가 충돌하지 않게 한다. 레시피 버전, 리그 프로필 버전, FPS와 seed를 Action 메타데이터에 남겨 재현한다. 같은 환경·입력의 수치 재현성을 목표로 하며, Blender 버전이 달라도 비트 단위로 동일하다고 보장하지 않는다.

### 모션 생성 엔진

- 동작별 주요 포즈와 위상 곡선을 만들고, 회전은 쿼터니언 보간을 사용한다. 모든 동작을 단순 사인파 하나로 처리하지 않는다.
- 대기: 호흡, 작은 골반 이동, 머리 지연 움직임을 서로 다른 위상으로 구성한다.
- 손 흔들기: 팔 올리기 → 손목·전완 반복 → 팔 내리기를 분리한다.
- 걷기: 지지·스윙 구간, 발바닥 목표, 골반 궤적, 팔 스윙을 함께 계산한다. 이동 속도와 보폭·주기를 연동한다.
- 스타일은 검증된 파라미터 묶음으로 정의한다. 예를 들어 활기찬 걷기는 팔 스윙·몸통 상하 이동·템포를 조절하되 접촉 제약을 유지한다.
- 초기에는 동작 하나씩 생성한다. 이후 순차 연결과 상체 마스크 합성을 추가하고, 합성 후에도 접촉을 다시 보정한다.

## 5. 리그와 IK: 핵심 개발 난점

본 이름 매핑은 탐색의 출발점이다. 실제 변환에는 부모 계층, rest pose, 로컬 축·bone roll, 길이, 객체 스케일, 관절 가동 범위, 컨트롤러 공간이 필요하다.

`RigProfile`에는 의미 본 매핑, 기준 자세 변환, 체형 길이, 발바닥 접촉 오프셋, IK 목표·pole, IK/FK 속성 및 지원 기능을 저장한다. 자동 탐지는 제안으로 제공하고 사용자가 확인·수정할 수 있게 한다.

기준 프로필은 샘플 조사 후 선택한다.

- 지원 가능한 컨트롤 리그라면 해당 컨트롤 본과 커스텀 속성을 구동한다. 생성 리그의 DEF 본을 무조건 직접 회전시키지 않는다.
- 단순 FK 스켈레톤이라면 별도 내부 제어 리그에서 IK를 계산하고 대상 FK 본으로 베이크하는 경로를 검토한다.
- IK/FK 전환과 임의 리그 지원은 어댑터마다 검증해야 한다. MVP에서 일반화하지 않는다.

보정은 대상 캐릭터 비율로 변환한 뒤 수행한다. 접지 높이뿐 아니라 지지 구간의 발 위치 고정, 골반 높이 조절, 도달 가능한 다리 길이, 무릎 방향, 발 회전을 처리한다. 제자리 걷기는 가상 루트 이동을 포함한 기준으로 접촉을 검사하고, 이동 걷기는 월드 공간 기준으로 검사한다. 초기 바닥은 평면으로 한정한다.

Blender 연결부는 객체 Transform과 PoseBone Transform을 구분한다. 대상 버전의 Action API에 맞춰 키를 넣고, 제약 적용 후 평가된 포즈를 베이크하여 재로드 결과를 검증한다. 기존 Action을 보존하고 생성 결과마다 별도 Action을 사용한다.

## 6. MVP 범위와 사용 흐름

**최소 성공 단위:** 기준 캐릭터 한 개에서 대기와 손 흔들기가 자연스럽게 생성되고, 반복 생성·취소·저장 후 재생이 안정적이다.

**첫 실용 버전:** 위 결과에 걷기와 발 접촉 검증을 추가한다. 이후 끄덕임·놀람·짧은 점프 순으로 확장한다. 소품 상호작용, 계단, 격투, 두 캐릭터 접촉, 손가락·표정은 초기 범위에 넣지 않는다.

사용 흐름은 캐릭터 선택 → 리그 프로필 확인 → 동작·길이·강도 설정 → 미리보기 → 조절 → Action 확정이다. 자연어 기능은 동일한 설정값을 채워 주며, 지원 범위를 넘는 요청을 조용히 다른 동작으로 바꾸지 않는다.

## 7. 단계별 구현과 완료 조건

아래 작업량은 1인 개발과 에이전트 보조를 가정한 초기 추정이며, 리그 조사 후 다시 산정한다. 렌더링 시간이나 모델 설치 시간을 보장하는 일정은 아니다.

| 단계 | 예상 작업일 | 산출물 | 다음 단계 진입 조건 |
| --- | --- | --- | --- |
| 0. 리그 조사 | 1~2일 | 기준 리그 프로필, 테스트용 복사본, 지원 Blender 버전 | 좌우·축·스케일·기준 자세·컨트롤러 확인 |
| 1. 최소 생성 경로 | 3~5일 | MotionSpec, 대기·손 흔들기, 별도 Action | 실제 Blender 등록·생성·취소·베이크·재로드 통과 |
| 2. 걷기 | 5~10일 | 접촉 구간, 발 IK, 루트 이동, 루프 보정 | 접촉·루프 수치와 재생 검토 통과 |
| 3. 제품화 | 3~5일 | UI, 리그 설정 저장, 자체 레시피, 개발 실행기 | 오프라인 반복 사용 및 원본 보존 확인 |
| 4. 선택적 자연어 | 2~4일 | 로컬 LLM 어댑터, 스키마 검증, 실패 처리 | 고정 문장 집합에서 의도 해석 평가 통과 |
| 5. 범위 확대 | 별도 산정 | 두 번째 리그, 합성 동작, 외부 모션 입력 | 동일 테스트가 두 번째 리그에서도 통과 |

실용 버전까지 약 12~22 작업일을 초기 가정으로 삼는다. 일정이 넘치면 동작 수와 지원 리그 수를 줄인다. 접촉 품질과 원본 보존 기준을 낮추지 않는다.

구현 파일은 `core/`에 동작·시간·보간·검증, `rigs/`에 프로필과 변환, `blender/`에 UI·Action·베이크, `recipes/`에 승인된 데이터, `providers/`에 선택적 자연어 연결을 분리한다. 이는 제안 구조이며 아직 생성하지 않았다.

macOS `scripts/dev_run.sh`와 Windows `scripts/dev_run.ps1`, `scripts/dev_run.bat`을 함께 준비한다. 일상 Blender 설정과 분리한 개발 프로필에서 로컬 소스를 로드한다. 배포 준비는 로컬 검증 이후 별도 단계다.

## 8. 검증 기준과 중단 기준

아래 수치는 초기 합격 기준 제안이며 측정 결과가 아니다. 체형과 캐주얼 표현을 보고 조정하되 변경 근거를 남긴다. 수치가 좋아도 재생 품질이 나쁘면 승인하지 않는다.

- 기준 캐릭터 높이를 H로 두고, 평면 지지 구간 발바닥의 수평 이동은 시작 접촉점 대비 최대 0.005H 이하, 바닥 침투 깊이는 0.002H 이하를 목표로 한다. 발 회전·뒤꿈치 들기 구간은 접촉 정의를 따로 둔다.
- 루프는 마지막 중복 경계 샘플과 첫 샘플의 관절 회전 차이 1도 이하, 위치 차이 0.002H 이하를 목표로 한다. 루트 이동량은 제거한 뒤 비교하고 경계 속도도 검사한다.
- 프레임 간 회전 튐·무릎 반전·NaN·무한값이 없어야 한다. 극단 강도·짧은 시간·긴 시간도 검사한다.
- 원본 Action·리그·장면 설정을 보존하고, 취소나 예외 시 미완성 결과를 정리한다. 저장 후 재로드된 베이크가 미리보기와 일치해야 한다.
- 고정 입력과 seed를 반복해 같은 환경에서 허용 오차 내 동일 결과를 얻는다.
- 기준 클립을 정면·측면에서 전체 재생한다. 몇 장의 스크린샷만으로 움직임 품질을 판정하지 않는다.
- 선택적 자연어는 지원 요청 30개·범위 밖 요청 10개부터 작성한다. 지원 요청의 동작·좌우·길이 해석 정확도 90% 이상을 초기 목표로 하고, 잘못된 JSON은 100% 차단한다.

첫 리그에서 접촉이 해결되지 않으면 리그 확장을 멈춘다. 손 흔들기조차 어색하면 자연어 기능보다 포즈·타이밍을 먼저 고친다. 로컬 LLM이 장비에서 너무 느리거나 부정확하면 프리셋 모드를 유지한다. 모델 유무가 생성 엔진의 사용 가능성을 좌우해서는 안 된다.

## 9. 로컬 AI 모델 도입 판단

MDM 공식 저장소는 코드가 MIT이지만 의존 라이브러리와 데이터에는 각각의 라이선스가 적용된다고 명시한다. 모델 입력·출력을 CatAni의 중간 포즈 형식으로 변환하고 접촉 보정을 거쳐야 하므로, 다운로드만으로 Blender 리그에 바로 적용된다고 가정하지 않는다. [MDM 공식 저장소](https://github.com/GuyTevet/motion-diffusion-model)

HY-Motion 공식 문서는 표준 모델 최소 VRAM 26GB, Lite 24GB를 안내하며, 짧은 모션·단일 seed 등의 조건을 덧붙인다. macOS 지원을 명시하지만 현재 장비에서 실행 가능하거나 실용 속도라는 뜻은 아니다. 비인간형과 복잡한 감정 표현도 제한 사항에 포함한다. 따라서 현 단계에서는 선택적 비교 대상으로 둔다. [HY-Motion 공식 저장소](https://github.com/Tencent-Hunyuan/HY-Motion-1.0)

AMASS 등록 페이지는 비상업적 연구 목적 조건을 명시한다. 초기 계획의 “AMASS를 애드온에 내장”은 기본안에서 제외하고 자체 포즈·자체 동작으로 시작한다. 외부 자료 도입 시 코드·가중치·학습 데이터·배포할 모션의 조건을 구분해 확인한다. [AMASS 이용 안내](https://amass.is.tue.mpg.de/register.php)

자연어 기능은 Ollama 같은 로컬 실행기의 JSON Schema 출력을 활용할 수 있다. 스키마 형식이 맞아도 동작 의미와 수치 범위는 CatAni에서 다시 검증한다. 모델은 장비와 한국어 평가 결과를 보고 정한다. [Ollama 구조화 출력 문서](https://docs.ollama.com/capabilities/structured-outputs)

추론 프로세스는 Blender Python 환경과 분리한다. 통신에는 시간 제한과 취소를 두고, 씬 변경은 Blender 메인 실행 경로에서 처리하도록 설계한다. 로컬 모션 모델 비교는 기본 엔진 완성 후 같은 요청으로 생성·리타게팅·보정·베이크까지의 시간과 품질을 측정한다. 절차적 방식보다 이득이 확인되는 동작에만 채택한다.

## 10. 첫 구현 착수안

`Player_Animation_01.blend`의 복사본으로 리그를 조사하고, **API와 LLM 없이 오른손 인사 Action 하나를 생성·재생·베이크하는 수직 시제품**부터 만든다. 이것이 통과하면 대기, 걷기, UI, 자연어 순으로 확장한다. CatAni의 첫 자산은 검증된 동작을 반복해서 생성하고 수정할 수 있는 엔진이다.
